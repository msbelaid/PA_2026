* The search problem

** Finding a student
*** Example
:PROPERTIES:
:BEAMER_col: 0.4
:BEAMER_env: column
:END:
|   ID | Name     |
|------+----------|
| 1023 | Ahmed    |
| 1045 | Mohammed |
| 1087 | Lina     |
| 1120 | Sara     |

*** Question
:PROPERTIES:
:BEAMER_col: 0.6
:BEAMER_env: block
:END:
How can we quickly find the name of the student with ID =1087=?

\pause

What if the list contains 100 000 students?

#+BEGIN_EXPORT latex
\note{
Start with the concrete task rather than the definition. 
Ask students how they would solve it manually. Let them suggest scanning the list.
The purpose is to establish the lookup problem and its cost.
}
#+END_EXPORT

** Naive solution: linear search
#+begin_src java
for (int i = 0; i < students.length; i++) {
    if (students[i].id == targetId) {
        return students[i].name;
    }
}
#+end_src

- Check entries one by one.
- In the worst case, inspect every entry. \pause
- Time complexity: $O(n)$.

#+BEGIN_EXPORT latex
\note{Explain that n is the number of entries. If the target is last, or absent, every entry may be inspected. Ask students what happens to the number of checks when the list doubles in size.}
#+END_EXPORT

** Better solution: binary search
- If entries are sorted by ID, compare with the middle entry.
- Discard half of the remaining entries at each step. \pause
- Time complexity: $O(\log n)$. \pause
- For \(n = 10^6\): \(\log_2 n \approx 20\) comparisons.

#+BEGIN_EXPORT latex
\note{
Binary search is a substantial improvement, but it requires sorted data and still performs comparisons.
Ask: can we locate a value directly, without searching through the array?
}
#+END_EXPORT

** Can we do better?
#+ATTR_BEAMER: :overlay <+->
- We want to look up a value using its key.
- We would like the lookup to be fast.
- Could we use the key to tell us where to look?

#+BEGIN_EXPORT latex
\note{
Do not introduce the term hash table yet.
Let students consider using the key as an array index.
Throughout the course, the key is the student ID and the value is the name.
This creates the need for the next section.
}
#+END_EXPORT

* From direct access to hashing

** Use the key as an index
#+begin_src java
String[] names = new String[2000];

names[1023] = "Ahmed";
names[1045] = "Mohammed";
names[1087] = "Lina";
names[1120] = "Sara";

// .......

System.out.println(names[1087]); // Lina
#+end_src

- No search is needed.
- Array access by index takes $O(1)$ time.

#+BEGIN_EXPORT latex
\note{
Assume for this example that IDs are valid array indices from 0 to 1999.
Point out that this is a strong assumption.
Direct access is excellent when the key range is small and manageable.}
#+END_EXPORT

** The problem with direct access
*** Example
:PROPERTIES:
:BEAMER_col: 0.7
:BEAMER_env: block
:END:
Suppose IDs are:
- Big number: ~8 700 087~
- UUID: ~5759456d-0ad2-4a3b-ba06-5bcac4f33481~
- Passport ID: ~P<DZABENMOHAMED<<MOHAMED~
  ~1234567891DZA8505204M2810243<<<28~
- String: ~"Name"~
- Any object type!

*** Problems
:PROPERTIES:
:BEAMER_col: 0.3
:BEAMER_env: alertblock
:END:
- A huge array may be required.
- Most positions may remain unused.
- Keys may not be integers.

#+BEGIN_EXPORT latex
\note{
Stress that direct access is not inherently bad.
It is unsuitable when the possible key space is much larger than the set of stored keys, 
or when keys cannot naturally be array indices.
}
#+END_EXPORT

** The idea: calculate an index
Instead of using the key directly, calculate an array index from it.


#+BEGIN_EXPORT latex
\[
\begin{array}{ccccc}
\text{Key} & \rightarrow & \text{Function} & \rightarrow & \text{Index} \\
1087 & \rightarrow & f(1087) & \rightarrow & 7
\end{array}
\]
#+END_EXPORT

\pause

Can we map many possible keys to a small array?

#+BEGIN_EXPORT latex
\note{
This is the conceptual bridge to hashing.
Ask students to suggest simple calculations that transform a large integer into a small range.
}
#+END_EXPORT

** A first hash function
Suppose the array has 10 positions, indexed from 0 to 9:
\(\quad h(k) = k \bmod 10\)

|  Key | Calculation | Index |
|------+-------------+-------|
| 1023 | 1023 mod 10 |     3 |
| 1045 | 1045 mod 10 |     5 |
| 1087 | 1087 mod 10 |     7 |
| 1120 | 1120 mod 10 |     0 |

\pause

#+BEGIN_EXPORT latex
\begin{center}
\begin{tikzpicture}[scale=0.75, transform shape]
  \probetable
\end{tikzpicture}
\end{center}
#+END_EXPORT

#+BEGIN_EXPORT latex
\note{
Every non-negative integer key maps to an index between 0 and 9.
Have students calculate h(1234), h(5678), and h(9999).
We keep this table of size 10 for the whole course: every drawing uses it.
}
#+END_EXPORT

** What is a hash table?
A *hash table* stores key-value pairs in an array.

- A *key* identifies an entry.
- A *value* is the data associated with that key.
- A *hash function* helps determine where the entry should be stored.

\(key \rightarrow hash function \rightarrow array index \rightarrow value\)

#+BEGIN_EXPORT latex
\note{
Use the student ID as the key and the name as the value.
Emphasize that the function determines a candidate position; 
it does not guarantee a unique position.
That limitation leads to collisions.}
#+END_EXPORT

** Properties of a useful hash function
\pause
- *Valid index:* the final index must be within the table.
- *Deterministic:* the same key gives the same result.
- *Efficient:* calculating the result should be inexpensive.
- *Good distribution:* keys should spread reasonably across positions.

#+BEGIN_EXPORT latex
\note{Avoid claiming that a good hash function prevents all collisions. It aims to distribute keys well. Let students answer the last question: the next section shows that the answer is no.}
#+END_EXPORT

* Collisions and chaining

** When two keys share an index
A new student arrives: *Yacine*, ID =2087=.
@@beamer:\uncover<2->{@@\quad \(h(2087) = 2087 \bmod 10 = 7\)@@beamer:}@@

  \draw[->, thick, red, visible on=<2->] (y) -- (7*1.4+0.7,0.9);
\end{tikzpicture}

#+END_EXPORT

@@beamer:\uncover<3->{@@Slot 7 already holds Lina (1087): this is a *collision*.@@beamer:}@@

#+BEGIN_EXPORT latex
\note{Ask students what would happen if insertion simply overwrote slot 7. Lina would be lost. A hash table must have a collision-resolution strategy.}
#+END_EXPORT

** Can we avoid every collision?
- Student IDs: thousands of possible keys.
- Our array: 10 positions.
- So several keys must share a position:
  7, 1087, 2087, 3087, ... all map to slot 7.

A better hash function can reduce collisions, but cannot eliminate them in general.

\pause
So where do we put Yacine?

#+BEGIN_EXPORT latex
\note{This is an instance of the pigeonhole principle. Keep the explanation intuitive: if there are more objects than boxes, at least one box must contain more than one object. The last question opens the two strategies.}
#+END_EXPORT

** Two main strategies
*** Separate chaining
:PROPERTIES:
:BEAMER_col: 0.48
:BEAMER_env: block
:END:
Each array position stores a list of entries.

#+BEGIN_EXPORT latex
\begin{center}
\begin{tikzpicture}[>=stealth, font=\scriptsize,
    k/.style={draw, fill=structure!15, minimum width=0.8cm, minimum height=0.4cm, anchor=west}]
  \foreach \i/\y in {6/0, 7/-0.45, 8/-0.9} {
    \draw[fill=gray!8] (0,\y) rectangle ++(0.6,0.4);
    \node[anchor=east] at (-0.05,\y+0.2) {\i};
  }
  \fill (0.3,-0.25) circle (1.2pt);
  \node[k] (a) at (1.0,-0.25) {1087};
  \node[k, fill=green!25] (b) at (2.2,-0.25) {2087};
  \draw[->] (0.3,-0.25) -- (a);
  \draw[->] (a) -- (b);
\end{tikzpicture}
\end{center}
#+END_EXPORT
2087 joins the list of slot 7.

*** Open addressing
:PROPERTIES:
:BEAMER_col: 0.48
:BEAMER_env: block
:END:
All entries stay inside the array. If a position is occupied, try another.

#+BEGIN_EXPORT latex
\begin{center}
\begin{tikzpicture}[>=stealth, font=\scriptsize]
  \foreach \i/\x in {6/0, 7/0.8, 8/1.6, 9/2.4} {
    \draw[fill=gray!8] (\x,0) rectangle ++(0.8,0.45);
    \node[font=\tiny] at (\x+0.4,-0.18) {\i};
  }
  \draw[fill=structure!15] (0.8,0) rectangle ++(0.8,0.45);
  \node at (1.2,0.225) {1087};
  \draw[fill=green!25] (1.6,0) rectangle ++(0.8,0.45);
  \node at (2.0,0.225) {2087};
  \draw[->, red] (1.2,0.5) to[bend left=50] (2.0,0.5);
\end{tikzpicture}
\end{center}
#+END_EXPORT
2087 takes the next free slot, 8.

#+BEGIN_EXPORT latex
\note{Introduce both strategies with the same collision: 1087 and 2087 both have index 7. The key contrast is where the second entry goes: into a list hanging from slot 7, or into another slot of the array. The list (the bucket) is drawn as a linked list, but any collection would do. Announce the plan: chaining first, in pictures then in Java; open addressing after.}
#+END_EXPORT

\end{tikzpicture}
\end{column}

\small
$m = 10$ buckets, \quad $h(k) = k \bmod 10$

\medskip
\uncover<2->{\alert<2>{Insert $x = (2087, \text{Yacine})$}}

\medskip
\uncover<3->{\alert<3>{\textbf{1.} Compute the index:\\
  \quad $h(2087) = 2087 \bmod 10 = 7$}}

\medskip
\uncover<4->{\alert<4>{\textbf{2.} Search 2087 in bucket 7:\\
  \quad $2087 \neq 1087$, end of the chain}}

\medskip

\end{tikzpicture}

\begin{column}{0.43\textwidth}
\small
\uncover<2->{\alert<2>{\texttt{get(2087)}: $h(2087) = 7$}}

\uncover<3->{\alert<3>{\quad $1087 \neq 2087$: next entry}}

\uncover<4->{\alert<4>{\quad $2087 = 2087$: return Yacine}}

\bigskip
\uncover<5->{\alert<5>{\texttt{get(3087)}: $h(3087) = 7$}}

\end{column}

\medskip
\begin{itemize}
\item Average chain length: $\alpha = n / m$ (the \emph{load factor}).
\item Insert, search, delete: $O(1 + \alpha)$ on average.
\item Worst case, all keys in one bucket: $O(n)$.
\end{itemize}
\note{With n entries spread over m buckets, a chain holds n/m entries on average. Computing the index is O(1), walking the chain is O(alpha). If alpha stays bounded, operations are O(1) on average. The bad hash function turns the table back into a linked list. Bridge: we now know the four operations in pictures; let us write them in Java.}

void put(int key, String value) {
    int index = hash(key); // (1)
    for (Entry entry : buckets[index]) { // (2)
        if (entry.key == key) {
            entry.value = value; // (3)
            return;
        }
    }
    buckets[index].add(new Entry(key, value)); // (4)
}
#+end_src

:PROPERTIES:
:BEAMER_col: 0.36
:END:
#+ATTR_BEAMER: :overlay <+->
1. Index of the bucket.
2. Walk the chain of that bucket.
3. Key found: update the value.
4. Key absent: append a new entry at the end of the list.

#+begin_src java
boolean remove(int key) {
    int index = hash(key); // (1)
    Iterator<Entry> it = buckets[index].iterator(); // (2)
    while (it.hasNext()) {
        if (it.next().key == key) {
            it.remove(); // (3)
            return true;
        }
    }
    return false; // (4)
}
#+end_src

* Open addressing

** Strategy 2: open addressing
Instead of a list, use another slot of the array.

All entries are stored directly in the array.

If the preferred position is occupied, probe other positions until:
- an empty position is found, or
- the desired key is found.

#+BEGIN_EXPORT latex
\note{Contrast this with chaining: no linked list is needed for collisions. The probing sequence must be consistent for insertion and lookup.}
#+END_EXPORT

** Linear probing
Try consecutive positions after a collision.

\[
h_i(k) = (h(k) + i) \bmod m
\]

- $h(k)$: initial index
- $i$: probe number, starting at 0
- $m$: table size

#+BEGIN_EXPORT latex
\note{For i=0, we try the original hash index. For i=1, the next position; for i=2, the next one, wrapping around at the end of the array.}
#+END_EXPORT

** Other probing strategies
Linear probing fills neighbouring slots: entries form *clusters*.
Other probe sequences jump further away:

- *Quadratic probing:* \(h_i(k) = (h(k) + i^2) \bmod m\)
  - for 2087 (\(m = 10\)): slots 7, 8, 1, 6, ...
- *Double hashing:* \(h_i(k) = (h(k) + i \cdot h'(k)) \bmod m\)
  - a second hash function \(h'\) chooses the step, so each key has its own sequence.

\pause
Same rules as linear probing: a search follows the same sequence,
and deletion uses tombstones.

#+BEGIN_EXPORT latex
\note{Do not go into details: the point is that linear probing is one choice among several. Quadratic probing and double hashing spread the probes and reduce clustering, at the price of a less cache-friendly access pattern. Choosing m and h' so that every slot can be reached is a subtle point, out of scope here.}
#+END_EXPORT

** Chaining vs. linear probing
| Property                  | Chaining                | Linear probing               |
|---------------------------+-------------------------+------------------------------|
| Storage                   | Bucket collections      | Array only                   |
| Collisions                | Add to same bucket      | Search for another slot      |
| More entries than slots   | Yes, longer chains      | No: the table can be full    |
| Main concern              | Long list               | Clustering                   |
| Deletion                  | Remove from list        | Tombstone                    |

#+BEGIN_EXPORT latex
\note{Use this slide to consolidate the contrast. Do not claim one strategy is always faster. Performance depends on the workload, load factor, memory behavior, and implementation details.}
#+END_EXPORT

* Load factor

** The load factor
How full is too full? We already met the measure in the cost of chaining:

\[
\alpha = \frac{n}{m}
\]

- $n$: number of stored entries
- $m$: number of table positions

Example: 7 entries in a table of capacity 10 gives $\alpha=0.7$.

\pause
When $\alpha$ grows, chains (or probe sequences) get longer and
operations slow down. With linear probing, $\alpha$ cannot exceed 1.

\(\Rightarrow\) Performance depends on keeping \(\alpha\) small.

#+BEGIN_EXPORT latex
\note{For chaining, the load factor is the average number of entries per bucket. For open addressing, it is the fraction of occupied slots and strongly affects the chance of finding an empty position.}
#+END_EXPORT

** Time complexity
With a good hash function and a bounded load factor:

| Operation | Average case | Worst case |
|-----------+--------------+------------|
| Search | $O(1)$ | $O(n)$ |
| Insertion | $O(1)$ | $O(n)$ |
| Deletion | $O(1)$ | $O(n)$ |

\pause
So far, all our keys were =int=. What about other keys?

\note{Avoid saying hash-table operations are always O(1). Worst-case behavior can be linear. The last line opens the next section.}

* Any key: strings and objects

** What if the key is a string?
Remember the keys that broke direct access:

Our =HashTable= only accepts =int= keys. \pause The idea, in two steps:

\[
\text{key} \xrightarrow{\text{hash code}} \text{int} \xrightarrow{\bmod\ m} \text{index}
\]

A string hash function combines information from its characters to produce an integer hash value.

** Computing a string hash: Java's String.hashCode()
*** Code

    int h = 0;
    for (int i = 0; i < s.length(); i++) {
        h = 31 * h + s.charAt(i);
    }
    return h;
}
#+end_src

\[
h(s) = s_0 \cdot 31^{n-1} + s_1 \cdot 31^{n-2} + \dots + s_{n-1}
\]

*** Example

| Char | Code | \(h = 31 h + \text{code}\) |
|------+------+--------------------------|

| i    |  105 | 2 461                    |
| n    |  110 | 76 401                   |
| a    |   97 | 2 368 528                |

:PROPERTIES:
:BEAMER_env: ignoreheading

\pause

#+BEGIN_EXPORT latex
\note{Both strategies of this course are used by real languages. Python keys must be hashable (immutable types such as int, str, tuple): this is the Python version of the hashCode/equals contract. In C++, operator[] inserts a default value when the key is missing, which is why count is used to test membership. The ordered counterparts, std::map and std::set, are trees, like Java's TreeMap.}
#+END_EXPORT

* Summary

** Key takeaways
- Direct access is the ideal case; hashing maps any key to an array position.
- Collisions are inevitable: chaining or open addressing resolves them.
- Lookup, insertion and deletion: $O(1)$ on average, $O(n)$ in the worst case.
- Hash quality and load factor matter.
- In Java, =equals()= and =hashCode()= must agree.
- Use standard collections in real applications; understand the implementation to use them well.
