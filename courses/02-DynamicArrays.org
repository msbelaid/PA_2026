* The problem: a fixed-size array

** Back to the open question
At the end of the Hash Tables course:

#+ATTR_BEAMER: :overlay <+->
- Our table has 10 slots and holds 10 students. Where does the 11th go?
- Answer: allocate a *larger array* and move the entries.
- But how much larger? And what does it cost?

\pause
The same question arises for *any* array: today we answer it on the simplest case,
a list of students.

#+BEGIN_EXPORT latex
\note{In Java, C and most languages, an array is a contiguous block of memory: its length is fixed when it is allocated, because the next bytes may already be used by something else. Ask students how they would choose the size: too small and we fail, too large and we waste memory.}

** Why not a linked list?
| Operation           | Array                   | Linked list              |
|---------------------+-------------------------+--------------------------|
| Access by index     | $O(1)$                  | $O(n)$                   |
| Append at the end   | $O(1)$, if room is left | $O(1)$ (with a tail)     |
| Memory              | Contiguous cells        | One node + pointer each  |
| Cache behaviour     | Excellent               | Poor (scattered nodes)   |

\pause
We want both:
- the *index access* and contiguous memory of an array,
- the *unlimited growth* of a linked list.

#+BEGIN_EXPORT latex
\note{Recall the complexity review of the introduction: "append in O(1)" had the footnote "if capacity allows". Linked lists from TP0 grow freely, but reaching element i means walking i nodes, and every node is a separate allocation. Contiguous memory is also faster in practice: the processor loads neighbouring cells into the cache together.}
#+END_EXPORT

** The goal: a dynamic array
A *dynamic array* is a list backed by an array, which grows when needed.

| Operation          | Meaning                              |
|--------------------+--------------------------------------|
| =get(i)=, =set(i, v)= | read or replace the element at index $i$ |
| =add(v)=           | append $v$ at the end                |
| =add(i, v)=        | insert $v$ at index $i$              |
| =remove(i)=        | remove the element at index $i$      |
| =size()=           | number of elements                   |

\pause
You already use it: =ArrayList= in Java, =list= in Python, =std::vector= in C++.

#+BEGIN_EXPORT latex
\note{Insist that this is one of the most used data structures in everyday programming: most "lists" students have written in Python are dynamic arrays. Understanding it explains when these operations are fast and when they are not.}
#+END_EXPORT

* Size and capacity

** Size vs. capacity
Idea: allocate *more cells than needed*.

\end{center}
#+END_EXPORT

- *Capacity:* number of allocated cells (=data.length=).
- *Size:* number of elements actually stored.
- Always: $0 \leq \text{size} \leq \text{capacity}$.

The free cells are invisible to the user: =get(6)= is an error.

#+BEGIN_EXPORT latex
\note{This distinction is the whole trick. The user only sees the first size cells; the remaining cells are reserved space for future appends. Ask: what is the size and the capacity of a new, empty list?}
#+END_EXPORT

* Growth strategies

** How much bigger?
Each resize copies all the elements: $O(n)$.

Two natural choices for the new capacity:
- *Strategy A:* add a constant: capacity $+ c$ (e.g. $+4$).
- *Strategy B:* multiply by a factor: capacity $\times 2$.

\pause
Let us count the copies for $n$ appends, starting from capacity 4.

#+BEGIN_EXPORT latex
\note{Let students vote before computing. Many will prefer +1 or +4 because it wastes no memory. The writes themselves always cost n in total: only the copies differ between strategies.}
#+END_EXPORT

** Strategy A: add a constant
Capacity: 4, 8, 12, 16, ... A resize happens every 4 appends.

#+BEGIN_EXPORT latex
\[
\text{copies} = 4 + 8 + 12 + \dots + (n-4)
             = 4\,(1 + 2 + \dots + k)
             \approx \frac{n^2}{8}
\quad \text{with } k \approx \frac{n}{4}
\]
#+END_EXPORT

\pause
- In general, with $+c$: about $\dfrac{n^2}{2c}$ copies: $O(n^2)$ for $n$ appends.
- A bigger $c$ only divides by a constant, and wastes more memory.
- Per append: $O(n)$ on average. As slow as inserting into a sorted array!

#+BEGIN_EXPORT latex
\note{The sum 1 + 2 + ... + k = k(k+1)/2 is the same as for the naive duplicate search of TP0. With c = 1, every single append copies the whole array.}
#+END_EXPORT

** Strategy B: double the capacity
Capacity: 4, 8, 16, 32, ... Resizes get *rarer and rarer*.

#+BEGIN_EXPORT latex
\[
\text{copies} = 4 + 8 + 16 + \dots + 2^j
\quad \text{with } 2^j < n
\]
#+END_EXPORT

\pause
A geometric sum: each term is larger than all the previous ones together.

#+BEGIN_EXPORT latex
\[
4 + 8 + \dots + 2^j = 2^{j+1} - 4 < 2 \cdot 2^j < 2n
\]
#+END_EXPORT

\pause
- Fewer than $2n$ copies for $n$ appends: $O(n)$ in total.
- Per append: $O(1)$ on average!

#+BEGIN_EXPORT latex
\note{The key fact: the last resize copies at most n elements, and all the previous resizes together copied fewer than that. Draw the sum as blocks on the board: 4 + 8 + 16 < 32.}
#+END_EXPORT

** Comparing the two strategies
Total number of copies for $n$ appends, starting from capacity 4:

| $n$          | $+4$                       | $\times 2$       |
|--------------+----------------------------+------------------|
| 16           | 24                         | 12               |
| 1 024        | 130 560                    | 1 020            |
| 1 000 000    | 124 999 500 000            | 1 048 572        |

\pause
At $\approx 10^9$ copies per second: *2 minutes* vs. *1 millisecond*.

#+BEGIN_EXPORT latex
\note{These are exact counts. Make students feel the difference: the constant strategy is not a little slower, it is in a different complexity class. Bridge: "O(1) on average per append" is a new kind of average; let us make it precise.}
#+END_EXPORT

** The aggregate method
Total cost of $n$ appends:

#+BEGIN_EXPORT latex
\[
T(n) = \underbrace{n}_{\text{writes}} + \underbrace{4 + 8 + \dots + 2^j}_{\text{copies} \,<\, 2n} < 3n
\qquad \Rightarrow \qquad \frac{T(n)}{n} < 3
\]
#+END_EXPORT

#+BEGIN_EXPORT latex
\begin{block}{Amortized cost}
The \emph{amortized cost} of an operation is the total cost of a worst-case
sequence of $n$ operations, divided by $n$.
\end{block}
#+END_EXPORT

\pause
Append in a doubling array: $O(1)$ amortized.

#+BEGIN_EXPORT latex
\note{This is the aggregate method: bound the total cost of the whole sequence, then divide. The word comes from finance: a large expense is amortized (spread) over a long period. The sequence starts from an empty array; the result holds for every n.}
#+END_EXPORT

** Amortized, average, worst case
| Kind of bound    | What is averaged?                  | Example                  |
|------------------+------------------------------------+--------------------------|
| Worst case       | nothing: the single worst operation | append: $O(n)$           |
| Average case     | over the inputs (or hash values)    | hash table get: $O(1)$   |
| Amortized        | over a sequence of operations       | append: $O(1)$           |

\pause
- The hash-table $O(1)$ assumes a good hash function: bad keys break it.
- The amortized $O(1)$ is a *guarantee*: it holds for *any* sequence. No probability.

#+BEGIN_EXPORT latex
\note{This distinction is often confused. Ask: can an adversary choose inputs that make appends slow on average? No: whatever the sequence, n appends cost less than 3n. For hash tables, an adversary who knows h can send keys that all land in one bucket.}
#+END_EXPORT

\small
\uncover<1->{\alert<1>{Just after a resize: capacity 8, half full, no coins saved.}}

\uncover<2->{\alert<2-4>{Each append pays 3 coins: 1 for its write, 1 saved on itself, 1 saved on an old element.}}

\uncover<5->{\alert<5>{The array is full: every element holds exactly 1 coin.}}

\uncover<6->{\alert<6>{Append Rania: 8 copies, paid by the 8 coins. Back to 0 coins, half full.}}

\note{This is the accounting method, used here as an intuition. Cheap operations are overcharged and the surplus is saved for the expensive ones. The account never goes negative, so the real total cost is at most 3 coins per append. Each round is the same story at twice the scale.}
#+END_EXPORT

** Why adding a constant fails
With capacity $+c$:
- After a resize, only $c$ appends happen before the next one.
- The next resize copies $n$ elements.
- To pay for it, each of the $c$ appends must save $\dfrac{n}{c}$ coins.

\pause
The price grows with $n$: no constant number of coins is enough.

\pause
With doubling, $m/2$ appends separate two resizes, and the next resize copies $m$ elements: 2 coins per append always suffice.

#+BEGIN_EXPORT latex
\note{Same picture, different conclusion. The point of doubling is that the time between two resizes grows as fast as the cost of a resize. Any factor greater than 1 has this property, with a different constant: we discuss this in practice at the end.}
#+END_EXPORT

** A single append can still be slow
- Amortized $O(1)$ does *not* mean that every append is $O(1)$:
  append $\#(2^k+1)$ copies $2^k$ elements.
- A problem for latency-sensitive programs: games, real-time systems,
  user interfaces.

\pause
If the final size is known, *reserve* the capacity upfront:

#+begin_src java
List<String> students = new ArrayList<>(100000); // no resize until 100000
#+end_src

#+BEGIN_EXPORT latex
\note{An amortized bound speaks about the total, not about each operation. A frame of a game that triggers a big copy may stutter. Reserving the capacity removes every resize. To go further: a third technique, the potential method, gives the same results more formally (CLRS, chapter "Amortized Analysis").}
#+END_EXPORT

* Implementing a dynamic array

** Implementation plan
1. Structure: an array and a size.
2. =get=, =set=: check the index against the *size*.
3. =add=: grow by doubling when full.
4. =add(i, v)=, =remove(i)=: shift the elements.
5. Test with our students.

Elements are =String= (student names).

#+BEGIN_EXPORT latex
\note{Same approach as the hash table: understand the mechanism with a simple element type, not reproduce every detail of ArrayList. A generic version DynamicArray<T> works the same way.}
#+END_EXPORT

** Structure
*** Code
:PROPERTIES:
:BEAMER_col: 0.64
:END:
#+begin_src java
class DynamicArray {
    private String[] data; // (1)
    private int size;      // (2)

    DynamicArray() {
        data = new String[4]; // (3)
        size = 0;
    }

    int size()     { return size; }
    int capacity() { return data.length; } // (4)
}
#+end_src

*** Explanation
:PROPERTIES:
:BEAMER_col: 0.36
:END:
#+ATTR_BEAMER: :overlay <+->
1. The cells: occupied and free.
2. The number of elements.
3. Initial capacity: 4, as in the drawings.
4. The capacity is the length of the array.

#+BEGIN_EXPORT latex
\note{Two fields are enough. The capacity does not need its own field: data.length already stores it.}
#+END_EXPORT

** get and set
*** Code
:PROPERTIES:
:BEAMER_col: 0.64
:END:
#+begin_src java
String get(int index) {
    checkIndex(index);
    return data[index];
}

void set(int index, String value) {
    checkIndex(index);
    data[index] = value; // (1)
}

private void checkIndex(int index) {
    if (index < 0 || index >= size) { // (2)
        throw new IndexOutOfBoundsException(
            "Index " + index + ", size " + size);
    }
}

** add(index, value) and remove(index)
*** Code
:PROPERTIES:
:BEAMER_col: 0.64

#+begin_src java
void add(int index, String value) {
    if (index < 0 || index > size) { // (1)
        throw new IndexOutOfBoundsException();
    }
    if (size == data.length) {
        grow();
    }
    for (int i = size; i > index; i--) {
        data[i] = data[i - 1]; // (2)
    }
    data[index] = value;
    size++;
}

String remove(int index) {
    checkIndex(index);
    String removed = data[index];
    for (int i = index; i < size - 1; i++) {
        data[i] = data[i + 1]; // (3)
    }
    size--;
    data[size] = null; // (4)
    return removed;
}
#+end_src

*** Explanation
:PROPERTIES:
:BEAMER_col: 0.36
:END:
#+ATTR_BEAMER: :overlay <+->
1. =index == size= is allowed: it appends.
2. Shift right, from the end.
3. Shift left, from the removed index.
4. Clear the last cell, so the garbage collector can free the object.

#+BEGIN_EXPORT latex
\note{Point 4 is easy to forget: without it, the array keeps a reference to an element that is no longer in the list (a memory leak in a garbage-collected language). Removing the last element moves nothing: O(1).}
#+END_EXPORT

* Shrinking

** Wasted memory
#+begin_src java
for (int i = 0; i < 1000; i++) students.add("Student " + i);
for (int i = 0; i < 990; i++)  students.remove(students.size() - 1);
#+end_src

- Size: 10, capacity: 1024. 99% of the cells are wasted.

\pause
Idea: *halve* the capacity when the array becomes sparse.

\pause
When exactly? The natural answer, "when it is half full", is a trap.

#+BEGIN_EXPORT latex
\note{Removing from the end is O(1), so this loop is fast; but the memory is never returned. Shrinking means allocating a smaller array and copying: O(n), like growing. Ask students to propose a threshold before the next slide.}
#+END_EXPORT

** First idea: shrink when half full
Grow $\times 2$ when full, shrink $\div 2$ when size $=$ capacity $/2$. Start: full, size $=$ capacity $= 4$.

#+BEGIN_EXPORT latex
\begin{center}
\begin{tabular}{llll}
\textbf{Operation} & \textbf{Size} & \textbf{Capacity} & \textbf{Copies} \\ \hline
\trow{2}{add: full, grow}       {5}{8}{4} \\
\trow{3}{remove: half, shrink}  {4}{4}{4} \\
\trow{4}{add: full, grow}       {5}{8}{4} \\
\trow{5}{remove: half, shrink}  {4}{4}{4} \\
\trow{6}{\dots}{}{}{}
\end{tabular}
\end{center}
#+END_EXPORT

@@beamer:\uncover<7->{@@Every operation copies $n$ elements: $O(n)$ each. This is *thrashing*.@@beamer:}@@

#+BEGIN_EXPORT latex
\note{With the coins: right after a grow, the array is exactly half full and the account is empty. A single remove then triggers a shrink, with no coins saved to pay for it. The sequence add, remove, add, remove is realistic: think of a stack whose size oscillates around a power of two.}
#+END_EXPORT

** Solution: shrink when a quarter full
#+BEGIN_EXPORT latex
\begin{center}
\begin{tikzpicture}[>=stealth, font=\small]
  \draw[thick] (0,0) -- (10,0);
  \foreach \x/\l in {0/0, 2.5/{$m/4$}, 5/{$m/2$}, 10/{$m$}} {
    \draw[thick] (\x,-0.15) -- (\x,0.15);
    \node[below=3pt] at (\x,-0.1) {\l};
  }
  \node[font=\scriptsize, gray, anchor=west] at (10.3,0) {size};
  \fill[structure] (5,0) circle (3pt);
  \node[structure, font=\scriptsize] at (5,-0.95) {after a resize};
  \draw[->, thick, red] (4.8,0.45) -- (2.6,0.45) node[midway, above, font=\scriptsize] {$\geq m/4$ removes};
  \draw[->, thick, green!50!black] (5.2,0.45) -- (9.9,0.45) node[midway, above, font=\scriptsize] {$\geq m/2$ adds};
  \node[red, font=\scriptsize\bfseries, align=center] at (2.5,1.25) {shrink $\div 2$};
  \node[green!50!black, font=\scriptsize\bfseries] at (10,1.25) {grow $\times 2$};
\end{tikzpicture}
\end{center}
#+END_EXPORT

- Grow $\times 2$ when full; shrink $\div 2$ when size $=$ capacity $/4$.
- After *any* resize, the array is exactly half full.
- At least $m/4$ operations happen before the next resize: they save enough coins.

\pause
\(\Rightarrow\) $O(1)$ amortized for *any* sequence of adds and removes.

#+BEGIN_EXPORT latex
\note{Check both cases with the students. Growing a full array of m elements gives capacity 2m with m elements: half full. Shrinking at m/4 elements gives capacity m/2 with m/4 elements: half full again. The gap between the two thresholds is what prevents thrashing.}
#+END_EXPORT

* Back to hash tables: rehashing

** The table is too full
Hash tables have the same problem: the load factor $\alpha = n/m$ grows.

- Java's =HashMap= doubles its number of buckets when $\alpha > 0.75$.
- Same idea as the dynamic array: grow by a *factor*.

\pause
Can we simply copy the buckets into a bigger array?

** The cost of rehashing
- Rehashing re-inserts all $n$ entries: $O(n)$, like copying an array.
- It happens when $\alpha$ crosses the threshold, and $m$ doubles each time.
- Same aggregate argument: =put= is $O(1)$ amortized (and on average, for a good hash function).

\pause
| Language | Initial buckets | Resize when        | Growth   |
|----------+-----------------+--------------------+----------|
| Java =HashMap= | 16        | $\alpha > 0.75$    | $\times 2$ |
| Python =dict=  | 8         | $\alpha > 2/3$     | $\times 2$ or more |

#+BEGIN_EXPORT latex
\note{For chaining, the threshold keeps the chains short. For open addressing, it is vital: probe sequences explode as alpha approaches 1, and the table can never exceed alpha = 1. Python uses open addressing, hence its lower threshold. Mention that a resize can make one put slow, exactly as for appends.}

* Dynamic arrays in practice

** Java ArrayList
#+begin_src java
List<String> students = new ArrayList<>();
students.add("Sara");          // append: O(1) amortized
students.add(0, "Ahmed");      // insert at the front: O(n)
students.get(1);               // Sara
students.remove(0);            // O(n)

ArrayList<String> big = new ArrayList<>(100000); // reserve the capacity
big.ensureCapacity(200000);    // grow once, now
big.trimToSize();              // capacity = size
#+end_src

- Grows by $\times 1.5$: =newCapacity = old + (old >> 1)=.
- Never shrinks by itself: call =trimToSize()=.

#+BEGIN_EXPORT latex
\note{The default capacity is 10, allocated at the first add. Careful with List<Integer>: remove(0) removes the element at index 0, while remove(Integer.valueOf(0)) removes the value 0. ArrayList trades memory for simplicity by never shrinking automatically.}
#+END_EXPORT

** Choosing the growth factor
Any factor $r > 1$ gives $O(1)$ amortized. The constant changes:

| Factor $r$ | Copies per append (amortized) | Wasted cells after a resize |
|------------+-------------------------------+-----------------------------|
| 2          | $\leq 1$                      | up to 50%                   |
| 1.5        | $\leq 2$                      | up to 33%                   |
| 1.125      | $\leq 8$                      | up to 11%                   |

\pause
A trade-off between *time* (fewer copies) and *memory* (fewer free cells).

#+BEGIN_EXPORT latex
\note{With factor r, the copies form the geometric sum n/r + n/r^2 + ... = n/(r - 1). Right after a resize, a fraction (r - 1)/r of the cells is free. Python favours memory because programs often hold many small lists; C++ libraries differ. There is no universally best factor.}
#+END_EXPORT

** Dynamic array vs. linked list
| Operation                | Dynamic array       | Linked list            |
|--------------------------+---------------------+------------------------|
| Access by index          | $O(1)$              | $O(n)$                 |
| Append at the end        | $O(1)$ amortized    | $O(1)$                 |
| Insert at the front      | $O(n)$              | $O(1)$                 |
| Insert after a known node | $O(n)$             | $O(1)$                 |
| Extra memory             | Free cells          | One pointer per element |
| Cache behaviour          | Excellent           | Poor                   |

#+BEGIN_EXPORT latex
\note{In practice, ArrayList is the default choice in Java, and LinkedList is rarely faster even for insertions, because walking to the insertion point is slow and cache misses dominate. Choose a linked list when you really insert or remove at known positions (or at the front) very often.}
#+END_EXPORT

* Summary

** Key takeaways
- A dynamic array separates *size* and *capacity*.
- Growing copies everything, $O(n)$: grow by a *factor*, never by a constant.
- Doubling makes append $O(1)$ *amortized*: a guarantee over any sequence.
- Shrink at $1/4$, not $1/2$, to avoid thrashing.
- Hash tables grow the same way: rehashing re-inserts every entry.
- In practice: reserve the capacity when the size is known.

#+BEGIN_EXPORT latex
\note{Ask students to explain the difference between amortized and average cost in their own words. A good answer: average is over the inputs and can fail on bad inputs; amortized is over a sequence and always holds.}
#+END_EXPORT
